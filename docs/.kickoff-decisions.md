## Locked in
- **Name:** Hammerline ("The Hammer" = Hamilton's nickname + production line). Tagline: "Maintenance & downtime tracking for the plant floor." Fictional seed plant: Bayfront Metal Works.
- Domain: manufacturing. Plant-floor maintenance & downtime tracker
- Timeline: no deadline; estimate ~75–100 hrs MVP (2–4 months part-time); every phase ends runnable
- Hosting: free tiers only
- Stack: keep Express 5 + TS backend and React 19 + Vite + Tailwind v4 frontend
- Roles: Operator, Technician, Supervisor (Supervisor also does admin)
- Core workflow ("breakdown loop"): report → machine Down (live) → triage/assign → in progress → resolve & log → Running → metrics
- MVP: auth + 3 roles + one-click demo logins; lines → machines (supervisor CRUD/archive); issue reporting; WO lifecycle with role-gated transitions + audit timeline; work log (notes, minutes, free-text parts); live status board; dashboard (downtime by machine/line, MTTR, MTBF, availability, open WOs by priority, date range); search/filter/sort/pagination; realistic seed data
- v2: preventive maintenance, parts inventory, sensor simulator + alerts, notifications/email, photo attachments, OEE, CSV/PDF export
- Out: multi-plant/multi-tenant, native mobile, real PLC integration, payments
- Data model: User, Line, Machine, WorkOrder, WorkOrderEvent, WorkLog, DowntimeEvent (+ RefreshToken for auth). Metrics derived from events via SQL
- Machine status RUNNING / DEGRADED / DOWN, recomputed from active work orders ("machine stopped?" flag). Tech resolves, supervisor closes. Single priority field
- Refinements (decided by Claude): CANCELLED status for duplicates (supervisor, from Open/Assigned); supervisor can reject a resolution (Resolved → In Progress); availability % included as honest OEE component; metrics assume 24/7 schedule in MVP
- DB: PostgreSQL (Neon prod), Prisma + raw SQL for metrics, docker compose locally
- Auth: supervisor-created accounts; demo logins (DEMO_MODE); JWT access 15m + opaque rotating refresh 7d (hashed, reuse detection) in httpOnly cookies; argon2; rate-limited login; requireAuth/requireRole; server-side WO state machine
- Real-time: Socket.IO, REST source of truth, emit after commit, TanStack Query invalidation, single-use socket ticket
- Hosting: Vercel (frontend, rewrite /api → Render), Render free (Docker), Neon; warm-up screen; nightly GitHub Actions demo reset
- Repo: npm workspaces (backend, frontend, shared)
- Frontend: React Router v7, TanStack Query, context + URL state, RHF + Zod, shadcn/ui, TanStack Table, Recharts, lucide-react, date-fns
- Backend: feature modules (routes→controller→service), app.ts/server.ts split, /api/v1, transitions endpoint, Zod validation, consistent error shape, page pagination, OpenAPI + Swagger UI at /api/docs, helmet, CORS allow-list, rate limit, env validation, pino + request IDs, health check, Sentry
- Testing (decided by Claude): Vitest everywhere; Supertest integration tests vs real Postgres test DB; RTL + MSW on frontend; Playwright E2E for breakdown loop (two contexts, live update) + axe a11y checks; coverage ≥80% on services/state machine
- CI/CD (decided by Claude): GitHub Actions ci.yml (lint, typecheck, test w/ Postgres service, build, docker build, e2e); Render auto-deploy after CI passes; Vercel previews per PR; demo-reset.yml nightly; Dependabot; Conventional Commits; branch protection; short ADRs in docs/adr
- UI direction (decided by Claude): industrial "control room" — calm neutral slate base, high-contrast status colours (green/amber/red) always paired with icon + text, light + dark themes, dense tables for supervisors, large touch targets for the operator tablet flow; IBM Plex Sans + IBM Plex Mono; WCAG 2.2 AA
- Build order: P0 foundations → P1 deployed walking skeleton → P2 auth & shell → P3 plant & machines → P4 work orders → P5 real-time → P6 dashboard → P7 hardening & launch
